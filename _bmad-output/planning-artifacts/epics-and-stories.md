# Epics & User Stories — MedLab

**Версия:** 1.0
**Дата:** 2026-03-20

## Epic 1: Безопасное хранилище данных
> Миграция с JSON-файлов на SQLite. Устранение race conditions и проблем масштабируемости.

### Story 1.1 — Создание SQLite базы данных
**Как** разработчик,
**Я хочу** инициализировать SQLite с нужной схемой и миграциями,
**Чтобы** все данные хранились надёжно с поддержкой транзакций.

**Acceptance Criteria:**
- [ ] Файл `db.js` создаёт подключение с WAL-режимом и включёнными foreign keys
- [ ] Папка `migrations/` содержит SQL-файлы начальной схемы
- [ ] При старте сервера автоматически применяются непримененные миграции
- [ ] better-sqlite3 инициализируется без ошибок
- [ ] Таблицы: `users`, `tests`, `test_parameters`, `family_members`, `attachments`, `jwt_blacklist`

**Оценка:** S (2-3 часа)

---

### Story 1.2 — Миграция существующих данных
**Как** пользователь с данными в JSON,
**Я хочу** автоматически перенести мои данные в SQLite,
**Чтобы** ничего не потерять при переходе на новую версию.

**Acceptance Criteria:**
- [ ] Скрипт `scripts/migrate-from-json.js` переносит данные из JSON-файлов в SQLite
- [ ] Скрипт проверяет: количество записей до и после совпадает
- [ ] JSON-файлы бэкапятся в `data/backup-pre-migration/`
- [ ] При повторном запуске скрипт не дублирует данные (idempotent)

**Оценка:** M (4-6 часов)

---

### Story 1.3 — Переписать API на SQLite
**Как** пользователь приложения,
**Я хочу** чтобы все мои действия (создание, изменение, удаление анализов) работали корректно,
**Чтобы** данные не терялись при одновременной работе нескольких пользователей.

**Acceptance Criteria:**
- [ ] Все CRUD-эндпоинты используют SQLite вместо JSON-файлов
- [ ] Создание/обновление анализа выполняется в одной транзакции (тест + параметры)
- [ ] Каскадные удаления работают (удалить тест → удаляются параметры и вложения)
- [ ] Все существующие e2e тесты проходят

**Оценка:** L (8-12 часов)

## Epic 2: Серверная безопасность
> Закрыть критические уязвимости: XSS, отсутствие валидации, незащищённые эндпоинты.

### Story 2.1 — Серверная валидация входных данных
**Как** владелец приложения,
**Я хочу** чтобы сервер отклонял невалидные запросы,
**Чтобы** защититься от инъекций и некорректных данных.

**Acceptance Criteria:**
- [ ] Установлен и настроен пакет `zod`
- [ ] Zod-схемы созданы для: register, login, createTest, updateTest, createMember, updateMember
- [ ] Middleware `validate.js` применяется к соответствующим роутам
- [ ] При невалидных данных возвращается `400` с описанием ошибки
- [ ] Тест: прямой POST без обязательных полей → 400

**Оценка:** M (4-6 часов)

---

### Story 2.2 — Фикс XSS в интерфейсе
**Как** пользователь,
**Я хочу** быть уверен, что вредоносный контент в анализах не навредит другим,
**Чтобы** мои данные были в безопасности.

**Acceptance Criteria:**
- [ ] Создан `public/js/utils.js` с функцией `escapeHTML()`
- [ ] Все места где `innerHTML` использует пользовательские данные заменены на `escapeHTML()` + `innerHTML` или на DOM API
- [ ] Тест: поле `conclusion` со значением `<img onerror=alert(1)>` → отображается как текст, не выполняется
- [ ] Тест: имя члена семьи с `<script>` тегом → отображается как текст

**Оценка:** M (3-5 часов)

---

### Story 2.3 — JWT revocation при logout
**Как** пользователь,
**Я хочу** чтобы после выхода из аккаунта мой токен стал недействительным,
**Чтобы** никто не мог использовать перехваченный токен.

**Acceptance Criteria:**
- [ ] Каждый JWT содержит уникальный `jti` (uuid)
- [ ] POST `/api/auth/logout` добавляет `jti` в таблицу `jwt_blacklist`
- [ ] Auth middleware проверяет blacklist при каждом запросе
- [ ] Ежедневная очистка истёкших записей из blacklist
- [ ] Тест: токен после logout → 401 на любой защищённый эндпоинт

**Оценка:** S (2-3 часа)

---

### Story 2.4 — Rate limiting на все эндпоинты
**Как** владелец приложения,
**Я хочу** ограничить количество запросов к API,
**Чтобы** защититься от DoS и брутфорс-атак.

**Acceptance Criteria:**
- [ ] Auth эндпоинты: 20 req / 15 мин (существующий лимит — сохранить)
- [ ] Остальные API эндпоинты: 200 req / мин на пользователя
- [ ] При превышении лимита: `429 Too Many Requests` + `Retry-After` заголовок
- [ ] Rate limit конфигурируется через `.env`

**Оценка:** S (1-2 часа)

## Epic 3: Управление анализами (улучшения)
> Пагинация, поиск, фильтрация для удобной работы с большим количеством данных.

### Story 3.1 — Пагинация списка анализов
**Как** пользователь с большим количеством анализов,
**Я хочу** видеть анализы постранично,
**Чтобы** приложение не тормозило и не загружало сотни записей разом.

**Acceptance Criteria:**
- [ ] GET `/api/tests?page=1&limit=20` возвращает `{ tests, total, page, pages }`
- [ ] По умолчанию: 20 записей на страницу
- [ ] Фронтенд показывает кнопки "предыдущая/следующая страница"
- [ ] При переходе между страницами URL обновляется (или state)

**Оценка:** M (4-6 часов)

---

### Story 3.2 — Поиск и фильтрация анализов
**Как** пользователь,
**Я хочу** быстро найти нужный анализ по параметрам,
**Чтобы** не листать весь список.

**Acceptance Criteria:**
- [ ] Поиск по: названию параметра, лаборатории, врачу, заключению
- [ ] Фильтр по: категории, диапазону дат, члену семьи
- [ ] Результаты обновляются по мере ввода (debounce 300ms)
- [ ] Пустой результат: показать сообщение "Анализы не найдены"

**Оценка:** M (4-6 часов)

## Epic 4: Профиль и аккаунт

### Story 4.1 — Удаление аккаунта
**Как** пользователь,
**Я хочу** удалить свой аккаунт и все данные,
**Чтобы** мои медицинские данные не хранились без моего желания (GDPR).

**Acceptance Criteria:**
- [ ] Кнопка "Удалить аккаунт" в разделе профиля
- [ ] Подтверждение: ввод пароля перед удалением
- [ ] DELETE `/api/account` удаляет пользователя и все связанные данные каскадно
- [ ] После удаления: редирект на страницу входа, токен инвалидируется

**Оценка:** S (2-3 часа)

---

### Story 4.2 — Сброс пароля
**Как** пользователь, забывший пароль,
**Я хочу** восстановить доступ к аккаунту,
**Чтобы** не потерять свои данные.

**Acceptance Criteria:**
- [ ] Страница "Забыли пароль?" с полем email
- [ ] Если email не настроен (нет SMTP в `.env`): генерируется временный токен, выводится на экран (dev-режим)
- [ ] Форма смены пароля с токеном
- [ ] Токен одноразовый, срок 1 час
- [ ] Новый пароль: мин. 8 символов

**Оценка:** M (4-6 часов)

## Epic 5: Качество кода

### Story 5.1 — Рефакторинг фронтенда на ES-модули
**Как** разработчик,
**Я хочу** разбить монолитный `app.js` (1771 строк) на модули,
**Чтобы** код было легче поддерживать и тестировать.

**Acceptance Criteria:**
- [ ] Созданы модули: `api.js`, `auth.js`, `tests.js`, `charts.js`, `members.js`, `pdf-parser.js`, `references.js`, `utils.js`
- [ ] Логика разнесена по модулям без дублирования
- [ ] Все e2e тесты проходят после рефакторинга
- [ ] `app.js` остаётся как главный роутер/инициализатор

**Оценка:** XL (12-16 часов)

---

### Story 5.2 — Логирование
**Как** владелец приложения,
**Я хочу** видеть логи запросов и ошибок,
**Чтобы** диагностировать проблемы в продакшне.

**Acceptance Criteria:**
- [ ] HTTP-запросы логируются через `morgan` (combined format в prod, dev format в dev)
- [ ] Ошибки приложения логируются с stack trace
- [ ] Логи пишутся в `stdout` (для Docker/systemd)
- [ ] Чувствительные данные (пароли, токены) не попадают в логи

**Оценка:** S (1-2 часа)
